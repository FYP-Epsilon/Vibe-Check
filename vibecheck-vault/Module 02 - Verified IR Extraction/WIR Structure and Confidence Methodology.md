> [!info] What this page is
> A plain-English, technical-but-accessible explanation of three things people keep asking about Module 02: (1) what the **WIR** actually looks like and represents, (2) how to read a WIR side-by-side with the code it came from, and (3) exactly how the **confidence formula** and its **decision threshold** were built — not just what the numbers are, but where they came from. Everything below is verified directly against the current source (`shared_schemas/wir_schema.json`, `module_02_extract/src/ast_extractor/`, `module_02_extract/src/dynamic_tracer/composer.py`, `module_02_extract/eval/calibrate.py`), and the worked example was actually generated by running the real extractor, not hand-written.

## 1. What the WIR is, in one paragraph

The **Workflow Intermediate Representation (WIR)** is Module 02's translation of a piece of Python code into a **map of boxes and arrows** — the same basic idea as a flowchart. Each box is a "node" (a step, a decision point, a loop, etc.), and each arrow is an "edge" showing what can happen after that step. It's stored as plain JSON, defined by a schema file (`shared_schemas/wir_schema.json`) that both Module 02 (which produces it) and Module 03 (which consumes it) agree to follow — think of the schema as the contract between the two modules: "this is exactly the shape of data I will hand you."

## 2. The two views of the same code — and why there are two

This is the single most important thing to understand about the WIR, because it's also where a real, measured bug used to live.

Python code is written in one order (you define all your functions first, then call them), but it *runs* in a different order (whichever function actually gets called, when, inside whichever branch). The WIR can be built either way:

- **Definition-order WIR** — walks the file top to bottom, in the order things are *written*. A function definition becomes a "task" box at the point it's *defined*, not where it's *used*.
- **Call-order WIR** (`call_order_wir`, also called the "driver" view) — instead follows the one function that actually *drives* the workflow (calls the other functions in real sequence, inside real if/else branches) and builds the map in the order things actually *happen* when the code runs.

**Why both exist:** Module 03 needs to check things like "does task B happen after task A?" — that question only makes sense against the *execution* order, not the *definition* order. Measured directly on real generated code: the definition order and the true execution order **disagree about task order in roughly 46% of real samples**. Before the call-order view was added, Module 03 was reading the wrong map nearly half the time. Both views are still produced — the definition-order view is kept for anything that already depends on it — but the call-order view is what actually gets used for checking a workflow against its rules.

## 3. Worked example — the same code, both WIR views, read side by side

Take this small, made-up piece of workflow code:

```python
def check_stock(order):
    return order["qty"] < 100

def charge_customer(order):
    return {"status": "charged"}

def ship_order(order):
    return {"status": "shipped"}

def workflow(order):
    if check_stock(order):
        result = charge_customer(order)
        ship_order(order)
    else:
        result = None
```

### 3.1 The call-order WIR (the one that matters for checking business rules)

This is the **actual, real output** produced by running Module 02's own extractor on the code above:

```json
{
  "entry_node": "node_1",
  "exit_node": "node_6",
  "nodes": [
    {
      "id": "node_1", "type": "gateway", "ast_type": "If", "line": 12,
      "guard": "check_stock(order)",
      "control_vars": ["check_stock", "order"],
      "successors": ["node_2", "node_4"], "predecessors": []
    },
    {
      "id": "node_2", "type": "task", "ast_type": "Assign", "line": 13,
      "code": ["result = charge_customer(order)"],
      "successors": ["node_3"], "predecessors": ["node_1"]
    },
    {
      "id": "node_3", "type": "task", "ast_type": "Expr", "line": 14,
      "code": ["ship_order(order)"],
      "successors": ["node_6"], "predecessors": ["node_2"]
    },
    {
      "id": "node_4", "type": "block", "ast_type": "Assign", "line": 16,
      "code": ["result = None"],
      "successors": ["node_6"], "predecessors": ["node_1"]
    },
    {
      "id": "node_6", "type": "exit",
      "successors": [], "predecessors": ["node_3", "node_4"]
    }
  ],
  "edges": [
    { "source": "node_1", "target": "node_2", "guard": "check_stock(order)" },
    { "source": "node_1", "target": "node_4", "guard": "not (check_stock(order))" },
    { "source": "node_2", "target": "node_3", "guard": null },
    { "source": "node_3", "target": "node_6", "guard": null },
    { "source": "node_4", "target": "node_6", "guard": null }
  ],
  "driver": "workflow"
}
```

**How to read this next to the source code, line by line:**

| WIR piece | What it is | The actual code it maps to |
|---|---|---|
| `node_1` (`type: gateway`, `guard: "check_stock(order)"`) | The decision point | `if check_stock(order):` |
| `node_1 → node_2` edge (`guard: "check_stock(order)"`) | The "yes" branch out of the decision | the path taken when the `if` is true |
| `node_2` (`type: task`, `code: "result = charge_customer(order)"`) | A real business action | `result = charge_customer(order)` |
| `node_3` (`type: task`, `code: "ship_order(order)"`) | The next real business action, right after `node_2` | `ship_order(order)` |
| `node_1 → node_4` edge (`guard: "not (check_stock(order))"`) | The "no" branch out of the decision | the `else:` path |
| `node_4` (`type: block`, `code: "result = None"`) | A step that isn't itself a tracked business action | `result = None` |
| `node_6` (`type: exit`) | Both branches rejoin here — end of the driver | the function returns |
| `"driver": "workflow"` | Which function this whole map was built from | `def workflow(order):` |

Notice: `charge_customer` and `ship_order` show up as `task` nodes **in the order they're actually called**, inside the correct `if` branch — that's the whole point of the call-order view. `check_stock` shows up as the **gateway's guard condition**, not as its own task box, because it's used to make a decision rather than being a tracked business step in this driver.

### 3.2 The same code's definition-order WIR (kept for legacy consumers, not used for rule-checking)

Running the *other* extractor path on the exact same source produces a very different-looking map — one `task` box per function, in the order they were **written** in the file:

```json
{
  "entry_node": "node_1", "exit_node": "node_2",
  "nodes": [
    { "id": "node_3", "type": "task", "ast_type": "FunctionDef", "line": 2, "code": ["def check_stock(...)"] },
    { "id": "node_4", "type": "task", "ast_type": "FunctionDef", "line": 5, "code": ["def charge_customer(...)"] },
    { "id": "node_5", "type": "task", "ast_type": "FunctionDef", "line": 8, "code": ["def ship_order(...)"] }
  ]
}
```

Notice this view has **no gateway, no guard, no branching at all** — it just lists the three function definitions in the order they appear in the file, one after another, as if they were a straight sequence. It doesn't know that `charge_customer` only runs when `check_stock` is true, or that `ship_order` runs right after `charge_customer` — that information only exists inside `workflow`'s own body, which this view never looks at (it becomes its own separate sub-map under a `functions` key instead, not part of this top-level list at all). **This is exactly why definition order and real execution order disagreed roughly 46% of the time** — a view like this simply doesn't contain the information needed to answer "what actually happens, and in what order?"

## 4. Every field, explained plainly

| Field | What it means |
|---|---|
| `id` | A unique name for this box, like `node_1`. |
| `type` | What kind of box this is: `task` (a real business action), `gateway` (a decision point), `loop`, `block` (an ordinary step that isn't individually tracked), `entry`/`exit` (start/end), plus a few for special Python constructs (`break`, `continue`, `return`, `except`, `finally`, `match`). |
| `line` | The line number in the original source file — for tracing a box back to exactly where it came from. |
| `code` | The actual source line(s) this box represents, kept as plain text. |
| `successors` / `predecessors` | Which boxes come right after / right before this one — this is what makes the map "walkable." |
| `guard` | If this box is a decision point (or the edge leading to/from one), the actual condition being tested — e.g. `"check_stock(order)"`. `null` when there's no condition. |
| `exception_type` | If this edge represents "what happens if an error is thrown," which kind of error. `null` otherwise. |
| `control_vars` / `data_vars` | Variables this box's decision depends on (`control_vars`) versus variables it just reads or writes as data (`data_vars`) — this distinction matters for a separate analysis step (V2's symbolic exploration) that needs to know which variables actually steer the workflow. |
| `driver` (call-order view only) | Which function in the file was identified as the one that actually drives execution — the one whose body got turned into this map. |

**One thing that's deliberately *not* in the WIR JSON itself:** dominance information (which steps *must* happen before which other steps can possibly be reached) is computed **separately**, from the WIR's graph, by a dedicated analysis (`dominators.py`) — it's not a stored field, it's something calculated on demand from the `successors`/`predecessors` structure above.

## 5. How the confidence formula was actually built

Module 02 produces a **confidence score** between 0 and 1 for how much you can trust that a piece of code matches its own extracted WIR. There are two different versions of this formula, used for two different purposes — mixing them up is the single easiest way to misread this project's numbers, so they're kept clearly separate here.

### 5.1 The production formula (what actually runs when you call `/verify`)

```
combined = 1 − (1 − v1) × (1 − v2)
```

This is implemented in `dynamic_tracer/composer.py`, and the reasoning behind this exact shape is direct and documented in the code itself: **v1 and v2 are treated as two independent pieces of evidence, and this formula is the standard way to combine two independent "this looks correct" signals into one** — the probability that *neither* check found a problem, phrased the other way round. It's the same shape of math used when combining independent detectors in general (this isn't project-specific cleverness — it's a standard combination rule, applied here to two specific checks).

**V3 (the structural check) deliberately does not appear in this formula at all.** An earlier version of the formula included a third term for V3, and it was removed on purpose: it turned out that any code that could be structurally parsed at all made V3's own term saturate to a very high, uninformative value, which padded the *combined* score regardless of whether the code was actually correct — making the whole verdict less meaningful, not more. Instead, V3 acts as a **gate**, not an ingredient: if V3 can't even build a trustworthy map of the code in the first place, the result fails immediately, no matter what V1 and V2 say — because checking V1/V2 against a bad map would be meaningless anyway.

`v1` itself (the dynamic-tracing score) is calculated as:

```
v1_confidence = (number of random test runs where the real code and the extracted map agreed ÷ total random runs) × a coverage score
```

In plain English: run the real code many times with different random inputs, separately "run" the extracted map as if it were a simplified version of the same code, and count how often they actually agree on what happened.

**The acceptance line for this production formula is fixed at 0.95** — code needs `combined ≥ 0.95` to be accepted and passed on to Module 03. This specific number (0.95) was set by hand as a deliberately strict bar, not derived from a statistical search — the statistical search described in §6 is a *different* threshold, for a *different* purpose.

### 5.2 The evaluation-only formula (used only when measuring detection rates, not at real request time)

When actually *measuring* how good Module 02 is at catching bugs (the numbers in `Module 02 Evaluation Results.md`), a **different, narrower formula** is used for the harder cases:

```
combined = v1   (V2's score is not used at all)
```

**Why V2 is dropped here, specifically:** in this evaluation mode, we deliberately compare a mutated (possibly buggy) version of the code against the *original, unmutated* program's map — not against its own map — because that's the only way to actually catch a real behavioral difference. But V2 (the symbolic solver) only ever explores the mutant's *own* code by itself, with nothing to compare against — so a high V2 score here just means "the mutant's code is internally consistent with itself," which is true whether or not it's actually buggy. Including it in the OR-formula was found to pad *every* score, correct and buggy alike, with a number that carried no real signal — so for this specific evaluation mode, the formula was changed to use V1 alone, and this change (and the reasoning behind it) is recorded directly in the evaluation report, not quietly changed with no trace.

## 6. How the threshold (tau) was actually chosen

This is a **separate number from the 0.95 acceptance line above** — don't conflate them. Tau is a decision line used **only inside the evaluation harness**, to answer the question "given this evaluation-only V1-based score, below what value should we call something 'probably buggy'?" It was not picked by hand. Here's exactly how it was chosen:

1. **Collect real scores for known-buggy and known-correct examples.** Take a large batch of programs — half deliberately mutated with a known bug, half left correct — and run every single one through the differential-mode formula from §5.2, producing one confidence score per program.
2. **Split the data in half first, before looking at any results.** Half of this batch (called CALIB) is set aside purely to *choose* the threshold; the other half (EVAL) is set aside purely to *measure* the final detection/false-alarm rates. The split uses a fixed random seed, so it can't be quietly re-shuffled to produce a nicer-looking result.
3. **Try every possible threshold value that could matter.** The code (`youdens_j_threshold()` in `calibrate.py`) doesn't guess a threshold — it takes every distinct confidence score that actually appears in the CALIB data (plus 0.0 and 1.0 as the two extreme boundaries) and treats each one as a candidate cutoff.
4. **For each candidate, compute Youden's J.** For a candidate cutoff `tau`, "predict buggy" means "this program's score is below `tau`." Youden's J is simply:
   ```
   J = (fraction of truly-buggy programs correctly predicted buggy)
     + (fraction of truly-correct programs correctly predicted correct)
     − 1
   ```
   J is a single number that rewards a threshold for catching real bugs *and* not crying wolf on correct code, at the same time — a threshold that's great at one but terrible at the other scores low; a threshold that's genuinely good at both scores close to 1.
5. **Keep whichever candidate threshold produced the highest J**, and freeze it. On this project's calibration data, the winning value was **tau = 0.1** (with J = 0.96), and it's saved to a small `threshold.json` file precisely so it can't drift between runs — the same frozen number is then applied, completely unchanged, to the EVAL half of the data to produce the actual detection-rate and false-alarm-rate numbers reported in the evaluation results.

**In plain English, tau = 0.1 means:** in this specific evaluation mode, if a mutated program's dynamic-tracing score comes back below 0.1, the harness calls it "probably buggy" — and that particular cutoff, out of every cutoff that was tried, was the one that best separated the truly-buggy examples from the truly-correct ones in the calibration half of the data.
