# P1.4 — LTLf→LTL Bridge: Investigation Findings

> Source: Claude Science, Session 01 (2026-07-29), run against the prompt in [[Claude Science Plan]].
> Full artifacts archived alongside this note: [[bridge_memo]] (design memo, 20-claim ledger) and
> `bridge_verification_log.txt` (raw experiment output E1–E8). Repo state examined: main @ `b791f2d`.
> This note adds an independent verification pass on top of the memo — spot-checking its
> source-level claims directly against the repo, and resolving one question the memo left open.

## Headline: the bridge is not primarily a semantics-conversion problem

Three separate defects surfaced, only the first of which the project's roadmap had named:

1. **Semantic gap (known, and solved).** SPOT 2.11.6 — the exact vendored version, confirmed
   pinned in both `module_01_spec/Dockerfile` and `module_03_equiv/Dockerfile` — ships
   `spot::from_ltlf()`, implementing the De Giacomo & Vardi finite-to-infinite reduction with two
   published paper errata already corrected upstream. **[VERIFIED-SOURCE, independently
   confirmed at `spot/tl/ltlf.hh:49`]**

2. **Vacuity defect — the one that actually decides the design.** Module 03's lifter never sets
   an acceptance condition (independently confirmed: `grep` for
   `set_buchi|set_acceptance|set_generalized_buchi` across `lifter.cpp` returns nothing), and
   exit states are explicitly allowed to have no outgoing edge (confirmed, `lifter.cpp` ~499-512).
   A terminating workflow therefore lifts to a finite, acyclic automaton with an **empty
   ω-language**. Consequence: **`check_compliance` returns `COMPLIANT` for every property on
   every non-looping workflow**, correct or not — this follows from standard Büchi automata
   theory once those two preconditions hold, independent of trusting the memo's own experiment.
   Module 03's own test suite documents this as intended semantics (independently confirmed
   verbatim: `test_cpp_engine.py:404`, `assert result.is_compliant is True  # vacuously true`) and
   only gets a real FAIL verdict via a deliberately looping fixture. **Not bridge-specific — live
   today**, dormant only because the sole caller passes a placeholder property nobody trusts
   (confirmed: `pipeline.py:57`, `'G("approved")'`). The moment P1.4 wires in a real property
   suite, this becomes a silent false-PASS on every ordinary (non-looping) LLM implementation.

3. **Vocabulary defect — confirmed independently, and resolved further than the memo left it.**
   Module 01's atoms (`done(Approve)`, `iteration_count <= 10`) are rejected outright by SPOT's
   parser; `FormulaNormalizer`, the apparent fix, has zero callers anywhere in the repo
   (independently confirmed by grep — the only hit is its own class definition) and only handles
   the `start`/`done` families, not `node(...)`.
   **Beyond what the memo resolved:** its self-declared "largest remaining unknown" — whether
   code-side and spec-side atom vocabularies intersect at all — was flagged as needing the
   compiled C++ container to answer. It doesn't. Reading `resolve_task_label` → `semantic_match`
   in `lifter.cpp` shows the matched BPMN task name becomes the automaton's AP directly via
   `ensure_ap(aut, matched)`, and there is **no `start_`/`done_` construction anywhere in the
   file** (zero grep hits for any lifecycle-prefixed AP assembly). So: **the vocabularies do not
   intersect, confirmed from source alone.** Module 03 emits one bare-task-name atom per action
   (e.g. `Approve`); Module 01 emits lifecycle atoms (`start_Approve`, `done_Approve`). Any spec
   property referencing the latter finds them permanently false in the code automaton — a
   second, quieter vacuity channel, now confirmed rather than hypothetical. Closing it needs a
   genuine **event-lifecycle mapping layer** (one code action ↦ a start/done AP pair), not just
   formula translation.

## Design tension noted, not yet decided

The `alive` reduction's `U(alive, G(!alive))` conjunct is unsatisfiable on a trace that stays
alive forever — so a hallucinated `while True: pass` would report VIOLATION on *every* property,
not because of what the code does but because it never terminates. This collides with Phase B's
deliberate divergence-sensitivity, which exists specifically to distinguish "diverged" from
"reached a bad state" rather than conflating them. The memo recommends a distinct
`NON_TERMINATING` verdict rather than folding divergence into ordinary property violation — a
reasoned design judgement, not yet a project decision.

## Two upstream Module 01 bugs surfaced (independent of the bridge)

- **Strong/weak `X` mismatch**: Module 01's `X` is strong — returns `False` past the trace end
  (independently confirmed, `ltlf_eval.py:166-169`); SPOT's bare `X` in `from_ltlf` is weak.
  Silent semantics flip at trace boundaries unless rewritten to `X[!]` before translation.
  Currently latent — none of the 12 sampled properties use `X` — but will bite as soon as the
  synthesizer emits one.
- **Tokenizer bug**: `TOKEN_SPEC`'s operator regex `\b[GfFXUW]\b` (independently confirmed,
  `ltlf_eval.py:11`) requires a word boundary on both sides, so an operator directly adjacent to
  its operand is swallowed into the atom name — `Gb` parses as an atom literally named `Gb`, not
  `G(b)`. A silent wrong answer, unrelated to the bridge, worth filing regardless.

## Confidence calibration — why this matters for how the memo gets cited

- **High confidence — independently re-derived from source, not just trusted:** the
  vacuity/false-PASS mechanism (source-confirmed preconditions + standard automata theory), the
  dead `FormulaNormalizer`, the parser's rejection of Module 01's atom syntax, the `X` strength
  mismatch, the tokenizer bug, and — beyond what the memo itself resolved — that the AP
  vocabularies do not intersect.
- **Credible, but not independently reconfirmed here:** that `alive`-instrumenting the automata
  actually produces correct verdicts in both directions (memo's experiment E4), and the
  12,600/12,600 differential-agreement figure validating the reduction end-to-end (memo's
  experiment E5). Both rest on a SPOT 2.11.6 build compiled locally in that Claude Science
  session, which has not been reproduced here. The memo itself labels these
  `VERIFIED-EXPERIMENT` rather than `VERIFIED-SOURCE` — an honest distinction worth preserving
  whenever this work is cited (in the thesis or otherwise).

## What this changes about P1.4's scope

Not a new P0 — nothing is down because of this, it's a latent defect, not a crash. But it
reshapes P1.4 from "translate LTLf strings to LTL" into a change on **both** sides: formula
translation + sanitization (Module 01 side) + automaton instrumentation for the `alive` AP
(Module 03 side) + an event-lifecycle mapping layer to close the vocabulary gap (new scope,
larger than originally assumed) + a vacuity guard before any `COMPLIANT` verdict is trusted. It
is also a caveat on Module 03's current "Phase D complete, real model checking" framing: accurate
for the mechanism, silently wrong on non-looping automata today. See updated [[Next Steps]] P1.4
entry and the corresponding caveat in [[Module 03 - Equivalence Engine/Module 03 Knowledge|Module 03 Knowledge]].
